**What the delta does.** `SetEpoch` used to clear `PlayedDay` and then return when the epoch was unchanged; now it returns first, so an unchanged epoch keeps the played day. A fork's or the shadow's `RestoreInto` sets the save's own epoch - the played world's - so it no longer clears the day the played world's seat map, legend and ink fence read; a new game on a new start still clears it, and a played world's own SetWorld or restore commits its day at once. The doubled CR was what made git store the file as non-text (H1); its removal restores the LF blob, so the branch-to-main diff is the real 16 lines. `CalendarDay` is no longer serialised, as its doc says. None of it books money, draws a random number or changes a figure the day loop computes; `PlayedDay` feeds only the dated bloc reading (`NationalElection.BlocOf`), which the no-policy dump never reaches (it tables no bill and seats no player).

**Risks.** A world opened at the same epoch by a NEW game would keep the previous game's played day until its first day - read in the code: a new game on the same start runs SetWorld, which commits its own day at once, so the stale day never reaches a reader. `SwedenBlocsDiagnostic` (f) proves the fork case (a shadow fork on 2026-06-10 leaves the played day and C at 0).
