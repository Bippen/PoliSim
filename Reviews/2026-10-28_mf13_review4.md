## The questions, answered

**(1) R3-1 on every preview path, and the standing origin.** `PreviewTurnOnClone` is now a one-line forward to `PreviewTurnOnCloneFrom(clone, id, decision, clone.State.ApprovalRating)`. The argument is evaluated at the call, and between the call and the old capture point only `DebtLimitCutFlowDay` is written, so `approvalBefore` is the same float the old code read: the plain `PreviewTurn` and `EstimateBudgetBill`'s standing clone are bit-identical to 7c662eec.
- `PreviewTurnWithBudgetDraft` reads the clone's approval before `ApplyBillResult` and passes it. With `draft == null` nothing runs between the read and the call, so the "standing" form is identical to `PreviewTurn`. Both clones come from the same real country, so both previews measure from the same origin, the real approval A. withDraft - standing = (-I) + I(1 - p^365) + (the daily and formula terms the draft's economy moves) = -0.81^4 x I plus the economy's share. That is the figure the game reaches a year on. The base B = approval + T is the same on both clones after `ChargeApproval` (A - I, T + I), so the reversion is unaffected, as review 3 established.
- `PreviewTurnWithSectorDraft`: `ApplySectorPolicyChanges` writes no approval, so the new origin is a no-op today. It is the consistent choice if it ever does.
- `EstimateBudgetBill`: the origin is now right, but `BudgetBillEstimate` exposes only revenue, spending and net, so no player figure moves.
- **Double counting.** No consumer adds the charge separately. `RecomputePolicyPreview` takes `withDraft.ApprovalChange - preview.ApprovalChange` for the effects arrow and `_cachedApprovalChangeRaw = withDraft.ApprovalChange` for Statistics, which adds it to the real `State.ApprovalRating`. That is the right origin now, where it was off by I before. The Desk card prints `shown.ApprovalChange` from `DeskEffectsPreview`, which returns `PreviewTurnWithBudgetDraft` results or the standing preview. No UI reads `ApprovalTerms`. Nothing charges `TaxHikeApprovalSensitivity` by hand anywhere in UI.

**(2) `DraftTaxCase`: teeth, state and order.**
- **The assertions are real outcomes.** I is measured on its own clone through the same `ApplyBillResult`. Then (a) I > 0.5 and charged = -I within 1e-4 (no clamp at Sweden's approval). (b) The previewed change less the clone's own ledger differs between the two previews by exactly the charge, within 1e-3. (c) The tax term's fading differs by I(1 - p^365), within 1e-3. Part (b) is the R3-1 assertion. It is robust to the draft also moving the economy, because every daily, formula and fading term is in the ledger on both sides, and `ChargeApproval` records nothing (the real callers record it around the call; the preview does not).
- **Teeth.** On 7c662eec `approvalBefore` was read after the bill, so the drafted residual was about 0 and `outsideLedger` about 0, against `charged` about -3 (1.5 x 2 VAT points, net 0 at the opening; Sweden's VAT is 25 against `VatMax` 30, so the clamp does not eat the rise). |0 - (-3)| far exceeds 1e-3, so the case FAILS on the old code. A VAT line missing or clamped fails loudly through `impulse > 0.5`, never as a silent pass. (c) passes on old and new alike. It pins the fading's linearity, not R3-1, which is fine.
- **Linearity of (c).** `TaxTerm.AdvanceDay` scales T by p each day and hands back exactly what fades while approval stays inside [0, 100]. So the gap is I(1 - p^365) up to float noise. The noise is about 365 roundings of approval near 50 (ulp about 3.8e-6, half-ulp each, pseudo-random sign) plus T's compounding: about 3e-5 to 1e-4 expected. The pathological worst case sums past 1e-3, but the run is seeded (777) and deterministic, so it is a fixed pass or fail, never a flake (I-2 below).
- **State and order.** The case runs after the `previews` and `dayTerms` dictionaries are captured and before any real boundary. Everything it does is on clones: the probe from `ClonePreviewCountry` by reflection, and the two previews. The fiscal-ledger "byte-untouched" check that follows now also covers these two previews, which is a small gain. The decision is a fresh `PolicyDecision.None()`, so `FinancePartner.Withdraw` restores nothing shared. The real world is unchanged, so the later sections see the state they saw at 7c662eec.
- **Compile.** Everything it touches is reachable: `ParliamentSystem.ApplyBillResult` (public static, a lambda for the `Action<Country, BudgetBill>`), `TaxTerm.DailyPersistence` (public static readonly float, widened for `Math.Pow`), `SimulationManager.DaysPerTurn`, `CurrentDate`, `BudgetBill.TaxLines` (initialised), and `System`/`System.Reflection` already imported.

## New findings

### R4-1 (Low, pre-existing premise now visible): a draft the government would not bear previews the government's tax charge
The preview always applies the draft with `ApplyBillResult(..., passed: true, ...)` and the default `governmentBears = true`. The game charges nothing in two cases:
- an alternative adopted over the government's frames (`ApplyBillResult(..., governmentAdopted)` at the budget division);
- a congressional author the president does not lead (`Congress.GovernmentBears`).

**Failure scenario:** the player sits in opposition (or in a support party) and drafts an alternative with a VAT rise. `RecomputePolicyPreview` runs `PreviewTurnWithBudgetDraft(decision None, the player's draft)`, and the Desk's `YourAlternativeTabled` subject does the same. The card now shows Approval -0.43 I against the government. If the alternative is adopted, the game charges 0 to the tax term, and approval moves by the economy's terms only. Before round 3 the same case showed +0.57 I. Both are wrong; the error is not introduced here, only flipped in sign and made the larger part of the figure. Not a blocker for MF-13, whose ruling is about the governing player's draft. **Fix (small, for a follow-up or this branch):** give `PreviewTurnWithBudgetDraft` the bearing flag the boundary would use (the player's role against the draft's author, as `GovernmentBears` reads it) and pass it to `ApplyBillResult`. Or declare the premise beside the Desk's scope line, as D4's "a draft counted whole" is declared.

### R4-2 (Info): `DraftTaxCase`'s bill also dissolves Sweden's fund
`new BudgetBill()` leaves `SwfShouldExist` false, and Sweden is seeded with a fund (`WorldFactory`, the `sweden.SovereignWealthFund` seed). So on the drafted clone `ApplyBudgetBillSpendingAndSwf` dissolves the fund and credits its assets to debt. The probe uses a no-op delegate and does not. None of the three assertions is affected:
- the dissolution writes no approval;
- its economic effect reaches approval only through ledger-recorded daily terms;
- the fading depends on T alone.

The case's log line ("budget draft VAT +2") under-describes the draft, though, and a future assertion on the economy would inherit a confound. Seed the bill's SWF fields from the country (`SwfShouldExist = country.SovereignWealthFund != null` and the current rate and weights), or say so in the summary.

### I-2 (Info): (c)'s 1e-3 is an empirical tolerance, not a bound
The daily hand-back's rounding is bounded only by 365 half-ulps per clone (about 1.4e-3 in all, worst case), against a tolerance of 1e-3. In practice the errors are pseudo-random and about 3e-5, and the run is deterministic. Record it beside the tolerance if it is ever tightened.

### I-3 (Info): one comment the round did not reach
`EstimateBudgetBill`'s summary still says each clone "is run through `PreviewTurnOnClone`". The bill's clone now runs through `PreviewTurnOnCloneFrom`. This is harmless (CommentClaimCheck reads only dotted names, and the method still exists and is the same body), but worth a word in the next pass. The `PreviewParityDiagnostic` header's "WHAT THIS ENUMERATES" paragraph does not list the draft case either. The rate-path section is not listed there today, so this is consistent with the file's practice, not a regression.
